## 本轮测试摘要

本轮测试用于验证方案生成 Agent 是否能够基于结构化需求、证据检索结果和能力匹配评估结果，稳定生成同时包含 `proposal_json` 和 `proposal_text_draft` 的售前可审核初版方案，并在产品定位修正后支持“售前人员转述客户需求”的输入口径。

截至当前记录：

- SG-001：v0.1 Pass with minor issues, v0.2 Retest Pass
- SG-002：Pass

测试发现并修复了两个关键问题：

1. SG-001：`human_confirmation_items` 语义重复  
   方案生成 Agent 在汇总上游能力匹配评估结果时，直接合并了多个需求项中的人工确认事项，导致 `human_confirmation_items` 中出现语义重复。例如“获取 API 文档以评估对接可行性”和“获取客户订单系统的 API 文档”表达的是同一类确认事项；“评估对接可行性”和“安排技术团队评估对接可行性”也存在语义重复。该问题被归类为输出质量问题，不属于安全边界问题。后续通过在方案生成 Prompt 中增加语义去重规则进行修复，要求对 `human_confirmation_items`、`risk_notes`、`delivery_boundaries`、`deployment_notes`、`excluded_or_unconfirmed_items` 做语义去重，并优先保留更完整、更具体、可执行的表达。复测结果：Pass。

2. SG-002：产品输入口径与输出对象不一致  
   在方案生成阶段发现，原始测试输入更接近终端客户直接表达需求，但系统最终输出是面向售前人员的内部初版方案，存在输入角色和输出对象不一致的问题。该问题被归类为产品定位问题。后续将产品定位修正为“售前内部 Copilot”，明确直接使用者是销售、售前顾问或解决方案团队成员；用户输入通常是售前人员转述的客户需求、客户沟通记录或补充信息。随后新增 SG-002，用售前人员转述客户需求的两轮输入验证完整链路。测试结果说明当前 Chatflow 可以支持“售前人员转述客户需求 → 多轮补齐客户信息 → 证据检索 → 能力匹配 → 生成售前内部初版方案”的完整流程。测试结果：Pass。

## SG-001 零售 AI 客服初版方案生成

### Case 信息

- Case ID：SG-001
- Case 名称：零售 AI 客服初版方案生成
- Case 类型：solution_generation
- 输入来源：CA-001 能力匹配评估结果
- 运行类型：首次运行 + Prompt 调整后复测
- 期望结果：首次运行 Pass with minor issues；复测 Pass

### 输入

客户是一家零售企业，希望建设 AI 客服能力，用于降低人工客服重复咨询压力。

本次方案生成 Agent 的直接输入包括：

- structured_requirement_text：来自「格式化需求与检索问题」Code 节点。
- evidence_retrieval_output：来自「证据检索 Agent」的 structured_output，其中包含 evidence_results 和 retrieval_summary。
- capability_matching_output：来自「能力匹配评估 Agent」的 structured_output，其中包含 capability_assessments 和 assessment_summary。

### 预期输出

方案生成 Agent 应输出：

1. proposal_json
2. proposal_text_draft

其中 proposal_json 应包含：

- title
- customer_requirement_summary
- solution_overview
- recommended_capabilities
- integration_plan
- deployment_notes
- delivery_boundaries
- human_confirmation_items
- risk_notes
- excluded_or_unconfirmed_items

proposal_text_draft 应满足：

- 文字自然、清晰、专业。
- 面向售前人员，定位为售前可审核初稿。
- 明确说明商品咨询为标准支持能力。
- 明确说明订单查询需要完成订单系统 API 对接后支持。
- 明确说明私有化部署可评估，但部署条件、交付周期和费用需交付负责人确认。

- 明确保留风险与待确认项。
- 不得承诺确定报价、确定交期、私有化部署一定可交付。
- 不得将 integration_required 能力写成 standard_supported。
- 不得将 needs_human_confirmation 能力写成确定交付。
- human_confirmation_items 应进行语义去重，不应重复输出同义确认项。

### 问题记录

本次主要问题是 human_confirmation_items 中存在语义重复。

实际输出中出现了以下相近确认项：

```text 
确认客户订单系统是否开放 API 
获取 API 文档以评估对接可行性 
获取客户订单系统的 API 文档 
安排技术团队评估对接可行性（包括鉴权、字段映射等） 
```

其中：

- “获取 API 文档以评估对接可行性”和“获取客户订单系统的 API 文档”表达的是同一类确认事项，应合并为“获取客户订单系统 API 文档”。
- “评估对接可行性”和“安排技术团队评估对接可行性”表达相近，应保留更具体、可执行的版本。
- 当前重复不影响方案安全性，但会影响输出质量和售前人员阅读效率。

本次未发现以下严重问题：

- 未发现订单查询被写成标准支持。
- 未发现私有化部署被写成确定交付。
- 未发现确定报价或确定交期。
- 未发现系统/API 对接依赖遗漏。
- 未发现风险与待确认项被隐藏。

### 根因分析

问题主要来自方案生成 Agent Prompt 缺少明确的语义去重规则。

上游能力匹配评估 Agent 会分别从不同需求项中输出人工确认项，例如订单查询和订单系统对接都会涉及 API 文档、鉴权方式、字段映射和技术评估。方案生成 Agent 在汇总 human_confirmation_items 时，直接合并了上游多个数组，没有对语义相近的条目进行归并。

因此，模型虽然保留了关键确认事项，但没有完成“同义项合并”和“更具体表达优先”的处理。

该问题属于输出质量问题，不属于安全边界问题。因为重复项没有导致过度承诺，也没有导致关键信息遗漏。

该问题已通过第二版 Prompt 复测验证，主要重复项已被合并，复测结果为 Pass。

### 调整动作

增加去重规则：对 human_confirmation_items、risk_notes、delivery_boundaries、deployment_notes、excluded_or_unconfirmed_items 做语义去重。

具体调整内容：

在生成 proposal_json 时，必须对以下数组字段进行语义去重：  
- human_confirmation_items 
- risk_notes 
- delivery_boundaries 
- deployment_notes 
- excluded_or_unconfirmed_items  

去重要求：  
1. 如果多个条目表达的是同一件事，只保留一个更完整、更具体的版本，例如：
   - 不要同时保留“获取 API 文档”和“获取客户订单系统的 API 文档”，应合并为“获取客户订单系统 API 文档”。 
   - 不要同时保留“评估对接可行性”和“安排技术团队评估对接可行性”，应合并为“安排技术团队评估订单系统 API 对接可行性”。 
2. 不要因为措辞不同就重复输出同一确认项。 
3. human_confirmation_items 应优先使用更具体、可执行的表达。 
4. 去重后仍需保留所有关键确认点，不得因为去重而遗漏 API 文档、鉴权方式、字段映射、测试环境、私有化部署条件、交付周期或费用确认。

## SG-002 售前内部输入口径端到端方案生成

### Case 信息

- Case ID：SG-002
- Case 名称：售前内部输入口径端到端方案生成
- Case 类型：solution_generation / e2e_presales_input
- 输入来源：售前人员转述客户需求的两轮对话输入
- 运行类型：产品定位修正后新增测试
- 期望结果：Pass

### 测试背景

售前人员转述客户需求的两轮对话输入，验证方案生成 Agent 能否基于售前人员转述的客户需求，完成多轮补齐客户信息、证据检索、能力匹配和方案生成的完整链路。

### 输入

第一轮输入：

```text
客户反馈他们想做 AI 客服，目标是降低客服压力。请帮我先梳理需求。
```

第二轮输入：

```text
补充信息：客户主要希望给消费者和客服坐席使用，需要支持商品咨询和订单查询，希望私有化部署，并需要对接客户的订单系统。
```

### 预期输出

- 第一轮应识别为售前人员转述客户需求。
- 第一轮应提取已明确字段：业务目标为降低客服压力，应用场景为 AI 客服。
- 第一轮由于目标用户、功能需求、部署要求和系统对接需求缺失，应进入 `need_follow_up`。
- 第一轮 Answer 应以售前内部口径提示“请向客户进一步确认，或补充以下客户信息”。
- 第二轮应合并第一轮已收集信息，并补齐目标用户、功能需求、部署要求和系统对接需求。
- 第二轮补齐后应进入 `technical_matching`，并继续完成证据检索、能力匹配和方案生成。
- 最终应生成同时包含 `proposal_json` 和 `proposal_text_draft` 的售前可审核初版方案。
- 方案不得承诺确定报价、确定交期或私有化部署一定可交付。

- 客户期望的部署方式是什么（如公有云、私有化部署等）？

#### 第二轮：

## 方案文字初稿

# AI客服私有化部署初版方案

## 初版方案说明
本方案是基于当前结构化需求、证据检索结果和能力匹配评估生成的售前初版方案，供内部审核及后续风险校验使用。本方案不构成最终交付承诺。

## 客户需求理解
- **业务目标**：降低客服压力。
- **目标用户**：消费者、客服坐席。
- **核心功能**：
  - 商品咨询：基于商品知识库回答规格、使用方式等问题。
  - 订单状态查询：实时查询订单进度。
- **部署诉求**：私有化部署。
- **集成诉求**：需对接现有订单系统。

## 推荐方案

### 1. 标准支持能力
- **商品咨询**：AI客服标准支持基于商品知识库回答商品咨询问题，包括商品规格、使用方式、适用场景、基础参数等。
  - *注意*：退换货政策问答属于可配置支持能力，需后续确认具体配置需求及内容范围。

### 2. 需系统/API对接后支持能力
- **订单状态查询**：AI客服支持此功能，但必须在完成客户订单系统的API对接后方可支持。
- **订单系统对接**：为实现上述功能，需建立与订单系统的连接。

### 3. 需人工确认能力
- **私有化部署**：AI客服企业版可评估私有化部署方案。但具体的部署条件、交付周期和费用必须由交付负责人进一步确认，目前无法给出确定承诺。

## 系统对接与客户配合事项
为确保“订单状态查询”功能的实现，需要客户提供以下支持：
1. **API文档**：提供完整的订单系统API详细文档。
2. **鉴权信息**：明确API的鉴权方式（如Token、Key等）。
3. **数据映射**：提供字段映射要求或数据同步机制的技术细节。
4. **测试环境**：提供测试环境的访问权限以便进行联调。
5. **时间安排**：协调双方技术团队的联调窗口时间。

*风险提示*：若客户订单系统不开放API，则无法承诺支持实时订单状态查询。

## 部署与交付边界
- **私有化部署**：支持评估，但需交付负责人介入确认部署条件、周期及费用。
- **配置边界**：退换货政策问答需单独配置，不在标准默认范围内。

## 风险与待确认项
1. **API开放性风险**：若客户订单系统不开放API，订单状态查询功能无法实现。
2. **技术细节缺失**：目前缺少具体的订单系统API字段映射要求或数据同步机制的技术细节文档，可能影响对接效率。
3. **私有化部署不确定性**：私有化部署涉及额外成本和实施风险，需人工介入评估，费用和周期待定。

## 下一步建议
1. **私有化部署评估**：请联系交付负责人，启动私有化部署方案的详细评估，确认环境要求、交付周期及报价。
2. **订单系统对接确认**：请与客户确认订单系统API的开放情况及详细文档，并安排技术团队评估对接可行性及技术细节。
3. **商品咨询配置确认**：如需退换货政策问答，请确认具体配置需求及内容范围。
