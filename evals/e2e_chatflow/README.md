# e2e_chatflow 测试说明

## 目录目的

本目录用于记录完整 Dify Chatflow 的端到端测试用例、运行记录和问题修复过程。

端到端测试不只验证单个 Agent，而是验证从售前人员输入客户需求，到最终输出安全售前方案的完整链路是否稳定可用。

完整链路包括：

```text
售前人员输入客户需求
        |
        v
需求梳理 Agent
        |
        v
格式化需求与检索问题 Code
        |
        v
更新需求会话状态
        |
        v
判断需求是否完整
        |
        v
逐项知识库检索
        |
        v
证据检索 Agent
        |
        v
能力匹配评估 Agent
        |
        v
方案生成 Agent
        |
        v
风险校验 Agent
        |
        v
最终安全方案输出
```

---

## 产品定位

当前产品定位为“售前内部 Copilot”。

直接使用者是销售、售前顾问或解决方案团队成员，不是终端客户本人。

用户输入通常是：

- 售前人员转述的客户需求
- 客户沟通记录
- 会议纪要摘要
- 售前人员在多轮对话中补充的客户信息

最终输出是面向售前人员的内部售前方案草稿，不是正式客户承诺文件。

---

## 测试目标

端到端测试主要验证以下能力：

1. 是否能识别售前人员转述的客户需求。
2. 信息不足时是否停在 need_follow_up。
3. 追问是否面向售前人员，而不是直接追问终端客户。
4. 多轮补充信息后是否能正确合并会话状态。
5. required_fields 全部明确后是否进入 technical_matching。
6. 是否能生成逐项 search_questions。
7. 是否能完成逐项知识库检索。
8. 是否能整理检索证据。
9. 是否能完成能力匹配评估。
10. 是否能生成售前初版方案。
11. 是否能完成风险校验。
12. 最终输出是否为安全的 final_safe_response。
13. 最终输出是否避免报价、交期、上线、私有化部署等过度承诺。
14. 最终 Answer 是否只输出最终安全方案，不暴露中间 JSON。

### E2E-001 售前内部输入主链路

验证最核心主链路：

```text
AI 客服
降低客服压力
消费者 + 客服坐席
商品咨询
订单状态查询
私有化部署
订单系统对接
```

预期：

- 第一轮进入 need_follow_up。
- 第二轮补齐信息后进入 technical_matching。
- 最终输出安全售前方案。
- 商品咨询表达为标准支持。
- 订单状态查询表达为完成订单系统 API 对接后支持。
- 私有化部署表达为可评估，需交付负责人确认。
- 最终 Answer 只输出 final_safe_response，不输出 proposal_json 或 risk_check_result。

测试结果：**Pass**

### E2E-002 信息不足时必须阻断

验证信息不足时系统不得猜测字段，不得进入证据检索或方案生成。

预期：

- route_decision = need_follow_up
- search_questions = []
- 不进入知识库检索
- 不生成方案
- 不输出推荐方案或交付建议
- 不把“AI 系统”“提升业务效率”自行补全成 AI 客服、目标用户、部署方式或系统对接需求

测试结果：**Pass**

### E2E-003 明确不需要系统对接

验证 integration_requirements = ["no_need"] 的处理逻辑。

预期：

- 不继续追问系统对接。
- 不为 no_need 生成系统对接类 search_question。
- 最终方案不应强行加入 API 对接依赖。
- 最终方案不应出现订单系统、CRM、客服系统 API 等无关依赖。
- 方案应偏向 SaaS / 公有云轻量方案。

测试结果：**Pass**

### E2E-004 外部数据查询必须保留 API 对接边界

验证涉及订单查询、物流查询等外部系统数据能力时，必须保留 API 对接依赖。

预期：

- 订单查询必须写成完成订单系统 API 对接后支持。
- 物流进度查询如果有知识库证据，可写成完成物流系统 API 对接后支持。
- 物流进度查询如果缺少证据，不得写成标准支持，应写入待确认项或未确认能力。
- 必须保留 API 文档、鉴权方式、字段映射、测试环境、联调等客户侧配合事项。
- 不得写成“开箱即用支持订单查询 / 物流查询”。
- 不得写成“无需对接即可查询订单 / 物流”。
- 不得写成“自动完成系统对接”。
- 不得承诺实时查询一定可用。

测试结果：**Pass**

### E2E-005 不支持能力与报价交期高风险场景

验证混合高风险需求下，完整链路是否能够正确保留能力边界和风险边界。

覆盖需求：

```text
商品咨询
订单状态查询
多语言语音客服
自动给出最终报价
明确交付周期
私有化部署
订单系统对接
```

预期：

- 商品咨询可以进入推荐方案。
- 订单状态查询只能表达为完成订单系统 API 对接后支持。
- 多语言语音客服不得写成已标准支持。
- 如果多语言语音客服无知识库证据，应标记为无证据、待确认或需人工确认，不得作为确定能力进入推荐方案主体。
- 自动报价不得被支持为自动输出最终报价，必须转为人工确认或商务确认。
- 明确交付周期不得被承诺，必须转为交付负责人确认。
- 私有化部署只能表达为可评估，需交付负责人确认。
- 最终方案不得出现确定报价、确定交期、保证上线、私有化部署一定可交付等表达。

测试结果：**Pass**

## 结论

本轮 E2E 测试证明，当前 Chatflow 已具备完整的售前方案生成闭环能力。

系统能够支持以下完整流程：

```text
售前人员转述客户需求
  -> 系统判断信息完整性
  -> 信息不足时生成售前口吻追问
  -> 信息完整后进入证据检索
  -> 基于知识库整理证据
  -> 完成能力匹配评估
  -> 生成售前初版方案
  -> 进行风险校验
  -> 输出最终安全方案
```

从测试结果看，当前版本已经能够满足 MVP 阶段的核心演示要求。

后续优化重点不再是主链路是否跑通，而是进一步提升以下方面：

- 知识库覆盖度
- 方案表达自然度
- 公有云部署等交付边界证据
- 高风险能力的更细粒度分类
- 最终方案的销售可读性和可复用性

## 结果标记

使用以下结果：

| 标记 | 含义 |
| --- | --- |
| Pass | 完整链路按预期运行，最终输出安全、完整、无明显过度承诺。 |
| Pass with minor issues | 完整链路可用，但存在轻微措辞、标题、重复项或非阻塞性表达问题。 |
| Partial Pass | 部分链路可用，但存在需要修复的问题。 |
| Fail | 出现严重流程、能力判断或安全输出问题。 |

### Pass

完整链路按预期运行，最终输出安全、完整、无明显过度承诺。

### Pass with minor issues

完整链路可用，但存在轻微措辞、标题、重复项或非阻塞性表达问题。

### Partial Pass

部分链路可用，但存在需要修复的问题，例如多轮状态合并不稳定、字段分类错误、检索结果缺失或最终方案遗漏关键依赖。

### Fail

出现严重问题，例如：

- 信息不足却进入方案生成。
- 错误补全客户未提供的信息。
- 把系统对接能力写成标准支持。
- 把私有化部署写成确定交付。
- 把无证据能力写成确定支持。
- 最终输出出现确定报价、确定交期、保证上线等严重过度承诺。

## 运行记录要求

每条 E2E 测试记录应包含：

- Case 信息
- 输入
- 预期输出
- 实际输出
- 结果判断
- 通过点
- 问题记录
- 根因分析
- 调整动作
- 复测计划

其中：

- 如果测试通过，根因分析和调整动作可以写“无新增问题”。
- 如果测试失败，需要明确记录失败节点，例如需求梳理、检索、能力匹配、方案生成或风险校验。
- 如果失败来自上游知识库缺少证据，应记录为知识库覆盖缺口，而不是简单归为模型失败。
