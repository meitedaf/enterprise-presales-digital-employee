本轮测试用于验证完整 Chatflow 的端到端可用性。

重点验证：

- 售前内部输入口径是否正确。
- 多轮需求补齐是否稳定。
- 信息不足时是否停在 need_follow_up。
- 信息完整后是否进入 technical_matching。
- 逐项检索是否能覆盖功能、部署和系统对接需求。
- 能力匹配是否正确识别标准支持、系统对接后支持、需人工确认能力和无证据能力。
- 方案生成是否完整、自然、可审核。
- 风险校验是否能输出安全的最终方案。
- 最终 Answer 是否只输出 final_safe_response。
- 最终 Answer 是否避免确定报价、确定交期、保证上线、私有化部署一定可交付等过度承诺。

## E2E-001 售前内部输入主链路：AI客服商品咨询订单查询私有化部署

### Case 信息

- Case ID：E2E-001
- Case 名称：售前内部输入主链路：AI客服商品咨询订单查询私有化部署
- Case 类型：e2e_chatflow
- 输入来源：售前人员转述客户需求的两轮对话输入
- 运行类型：首次运行
- 期望结果：Pass

### 输入

第一轮输入：

```text
客户反馈他们想做 AI 客服，目标是降低客服压力。请帮我先梳理需求。
```

第二轮输入：

```text
补充信息：客户主要希望给消费者和客服坐席使用，需要支持商品咨询和订单查询，希望私有化部署，并需要对接客户的订单系统。
```

### 预期输出

第一轮预期：

- 进入 need_follow_up。
- 不进入证据检索。
- 不输出方案。
- 输出面向售前人员的追问。
- 追问中应出现“请向客户进一步确认”或“补充以下客户信息”。
- 缺失字段包括：
  - target_users
  - functional_requirements
  - deployment_requirement
  - integration_requirements

第二轮预期：

- 合并第一轮已收集信息。
- 进入 technical_matching。
- 完成知识库检索、证据整理、能力匹配、方案生成和风险校验。
- 最终 Answer 只输出风险校验后的 final_safe_response。
- 最终方案包含：
  - AI 客服
  - 降低客服压力
  - 消费者
  - 客服坐席
  - 商品咨询
  - 订单状态查询
  - 私有化部署
  - 订单系统 API
  - 完成系统/API 对接后支持
  - 交付负责人确认
  - 不构成最终交付承诺
- 商品咨询表达为标准支持。
- 订单状态查询表达为完成订单系统 API 对接后支持。
- 私有化部署表达为可评估，需交付负责人确认。
- 不输出 proposal_json 或 risk_check_result。
- 不承诺报价、交期、上线或私有化部署一定可交付。

### 实际输出

#### 第一轮输出：

```text
当前客户需求信息还不完整，暂时无法进入证据检索流程。

请向客户进一步确认，或补充以下客户信息：
- 该 AI 客服系统主要服务哪些使用对象（如终端消费者、内部员工等）？
- 客户希望该 AI 客服具体支持哪些业务功能（如商品咨询、订单查询、退换货政策问答等）？
- 客户期望的部署方式是什么（如公有云、私有化部署等）？
- 是否需要对接现有系统（如 CRM、工单系统等）？如果需要，请确认具体系统名称。
```

#### 第二轮输出：

```text
# AI客服降低客服压力初版方案

## 初版方案说明
本方案是基于当前结构化需求、证据检索结果和能力匹配评估生成的售前初版方案，供内部审核及后续风险校验使用。本方案不构成最终交付承诺。

## 客户需求理解
- **业务目标**：降低客服压力。
- **目标用户**：消费者、客服坐席。
- **核心功能**：
  - 商品咨询：基于知识库回答商品相关问题。
  - 订单状态查询：实时查询订单进度。
- **部署诉求**：私有化部署。
- **系统对接**：需对接现有订单系统以获取订单数据。

## 推荐方案

### 1. 标准支持能力
- **商品咨询**：AI客服标准支持基于商品知识库回答商品规格、使用方式、适用场景、基础参数及售后规则入口等问题。该能力可直接启用。

### 2. 需系统/API 对接后支持能力
- **订单状态查询**：AI客服支持此功能，但必须在完成与客户订单系统的API对接后方可支持。若客户订单系统不开放API，则无法实现实时订单状态查询。
- **订单系统对接**：作为上述功能的基础，需建立与订单系统的数据连接。目前需进一步确认具体的技术对接细节。

### 3. 需人工确认能力
- **私有化部署**：AI客服企业版支持私有化部署方案的评估。但是，具体的部署条件、交付周期以及相关费用无法由系统自动承诺，必须由交付负责人根据客户具体环境进行评估和确认。

## 系统对接与客户配合事项
为支持订单状态查询功能，需要客户提供以下配合：
1. **API文档**：提供完整的订单系统API接口文档。
2. **鉴权方式**：明确API调用的鉴权机制（如Token、OAuth等）。
3. **字段映射**：提供订单数据的关键字段映射规范，以便AI客服正确解析订单状态。
4. **测试环境**：提供用于联调测试的API环境或沙箱账号。
5. **联调窗口**：协调双方技术人员进行接口联调的时间窗口。

*注意：目前证据中缺乏关于订单系统对接的具体技术细节（如数据同步频率、异常处理机制等），建议安排技术人员提前评估对接可行性。*

## 部署与交付边界
- **私有化部署**：可评估，但需进一步确认交付条件、周期和费用。具体实施风险和成本需由交付团队介入评估。
- **商品咨询配置**：退换货政策问答属于可配置支持能力，需确认是否需要针对退换货规则进行额外配置。

## 风险与待确认项
- **风险**：
  1. 若客户订单系统不开放API，则无法支持订单状态查询功能。
  2. 私有化部署涉及定制实施，存在交付风险和成本不确定性。
  3. 订单系统对接缺乏具体技术细节，需进一步评估。
- **待确认项**：
  1. 联系交付负责人评估私有化部署的具体方案和报价。
  2. 获取客户订单系统的API文档。
  3. 安排技术人员进行订单系统API对接可行性评估。
  4. 确认客户订单系统是否开放API接口。
  5. 确认API字段映射及鉴权方式。
  6. 确认是否需要配置退换货政策问答的具体规则。

## 下一步建议
1. 请售前同事尽快联系客户，获取订单系统API文档及技术细节，并安排技术团队进行对接可行性预评估。
2. 请售前同事联系内部交付负责人，启动私有化部署方案的初步评估流程，以获取大致的条件和费用范围。
3. 与客户确认退换货政策问答的配置需求，以便完善商品咨询能力的配置方案。
```
